# Moat = the Data, Not the Mechanism

_Section: Distributed-Harness Architecture (AOv2 / Agentic NorthStar) — part of `ai-product/`; router = README.md._
- **Date identified**: 2026-05-22
- **Source**: Pedro's framing in the Ian NorthStar thread, endorsed by Ian (*"a great way of putting it"*; tied to a senior early-March conversation with @lkao + @gmiller; Adobe Research active in the space).
- **Insight**: A capability built on open, portable standards (open API / MCP, fork-and-run) appears to conflict with lock-in (*"heartbreaking to leave"*). It resolves by separating layers: keep the **mechanism open** (interface, protocol) for adoption + portability; the **moat is the data** — the customer's accumulated content, context, and memory, costly to rebuild elsewhere. *Open interface, sticky data.* Ian's analogy: Gmail is portable (takeout) yet heartbreaking to leave because of the accumulated value on top.
- **Implication**: (1) **Positioning** — sell accrued value, not lock-in: *"you stay because leaving means rebuilding years of context,"* credible precisely because the interface is open. (2) **Measurable** — accumulated-memory value shows up as returning orgs/users + retention (the signal Pedro already owns). (3) For AEM, the customer's content *is* a primary memory source.
- **Refinement — the open layer is the *consumer-agnostic interface*, and the harness debate doesn't justify coupling to it (2026-06-17, P42 thread; Ian Reasor + Felix Meschberger, two independent voices)**: when Ian Boston argued APIs needn't stay API-First because Coworker is the front door for all traffic, Ian Reasor rebutted — *"replace Coworker with UI and you get the POV API First was built to counter."* A clean, standalone API serves four consumers at once (UIs, AI skills, MCPs, customer extensibility), so coupling it to one privileged consumer (a UI, or a harness) recreates the exact problem API-First was built to fix. *"We don't need hand-written harnesses to justify pursuing this architecture"* = keep the interface clean **for its own sake**, independent of which harness/orchestrator wins. Felix corroborates from the UI side: companion mode *"is a UI problem not a backend/harness problem… independent of the backend/harness."* Net: the durable, ownable layer is the **consumer-agnostic interface + the data/definition on top**; harness and UI are interchangeable consumers (two-way doors, in Pedro's door-map framing). **Test for moat-layer vs swappable consumer: does it serve multiple consumer types regardless of the harness?** Two senior voices stated this unprompted — strong corroboration of open-interface / sticky-data, and the architectural "why" behind Pedro's one-way (skills + interface + definition) vs two-way (harness, UI) classification.
