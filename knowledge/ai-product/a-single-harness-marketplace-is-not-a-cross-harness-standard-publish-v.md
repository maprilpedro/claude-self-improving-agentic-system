# A Single-Harness Marketplace Is Not a Cross-Harness Standard — Publish vs Find

_Section: Distributed-Harness Architecture (AOv2 / Agentic NorthStar) — part of `ai-product/`; router = README.md._
- **Date identified**: 2026-05-28
- **Source**: Pedro's AOv2 confirmation (2026-05-28) against the distributed-harness model; grounded in the 2026-04-29 AOv2 alignment transcript + AOv2 plugin docs (Confluence 3851715892).
- **Insight**: A per-harness plugin marketplace solves *supply within one harness* and nothing above it. AOv2's model is concretely git-native and local-copy: a marketplace git repo (template `OneAdobe/ao-plugin-extensions-template`) installed into a local AO. It does **not** address the cross-harness layer the distributed model needs: one consistent **declaration standard** so skills are described the same way across *different* harnesses (AEM's, CXO's, DMe's), a **shared discovery index**, and a **curation convention**. The reflexive objection "AOv2 already has a marketplace" conflates the two. The anchor that separates them: **publish vs find** — a marketplace is how a developer *publishes* a skill into a harness; the missing layer is how the right skill is *found and made present* across all of them. (Skill-level evals are a neighbouring unsolved gap: a harness can install skills it cannot evaluate at skill granularity — Trent, 2026-04-29.)
- **Why it matters**: the PM-ownable layer in a distributed-harness world is the standard + discovery + curation *above* any single harness's store. That is definition ownership ([[Definition Ownership Is the Moat on Shared Data Infrastructure]] in leadership/), not a competing service — and the stronger political position, because a standard is not a turf-fight while a central registry is (Ian's round-4 deflation). Naming "publish vs find" is what stops a cross-harness proposal from being dismissed as a duplicate of an existing marketplace. Keep this distinction in internal/architecture conversations, not in a public post that names the AOv2 gap by name (additive-not-corrective).

- **2nd-party corroboration from the platform owner (2026-06-15, Manas Garg, AOA):** the Coworker/AOv2 eng lead independently confirmed both halves. **Supply is decoupled:** *"creating a central show point did not work for anybody, including the central team… this time a fair amount of decoupling"* → teams set up **their own plugin marketplaces, registered into a central index, sourced/consolidated** (matches publish = per-team/git-native, not a central store). **The layer above is admitted-unsolved:** *"nobody knows the right way to organize these skills and MCPs at enterprise scale — this is the first time this problem is being solved in the industry."* = the "find / organize / curate across harnesses" gap, named open by the person who owns the platform. The **Coworker Agent Gateway** (agents discover capabilities + the gateway collects agent-journey analytics) is their "find + observe" layer, but the **organizing standard above it is the empty seat** — which is the PM-ownable lane, now confirmed vacant from the platform side, not just argued by Pedro. **Caveat to bank (framing tension):** Manas *deflates* "skills" — *"an overrated term… at the end of the day it is documentation for agents… a protocol for progressive disclosure"* (hooks/prefetch can do the same discovery). So the platform-eng view treats skills as docs+protocol, not a first-class primitive; pitch the lane as **"how capabilities are described + organized + found across harnesses,"** not "the skill standard," to avoid arguing the word with the engine owner.
- **Refinement — the industry is shipping "declare-to-be-discoverable" too (2026-06-08, MCP 2026 roadmap)**: the cross-harness "find" layer Pedro owns for *skills* has a direct analog for *tools* in the public MCP roadmap — **Server Cards**: a standard metadata file at a `.well-known` URL that lets clients, registries, and crawlers discover a server's capabilities (tools, resources, auth, transports) **without opening a live session** (think `robots.txt` / `.well-known/openid-configuration` for MCP servers; defined by the Server Card Working Group). MCP itself moved to the **Agentic AI Foundation under the Linux Foundation** (Dec 2025); its 2026 roadmap is Working-Group-owned (transport scalability, agent communication, governance maturation, enterprise readiness). **Why it matters for the PM line:** "declare your capabilities so they can be found" is now an *industry-standardized* pattern, not an AEM invention — which de-risks Pedro's skill declaration standard (it rides the same wave) and gives a public reference to cite: *"Server Cards are, for tools, what our skill declaration standard is for skills."* Also concretizes the skill file: a skill = a folder + `SKILL.md` (YAML frontmatter `name`/`description` + markdown body + bundled files), and **progressive disclosure** (L1 name+description always loaded / L2 body on demand / L3 bundled files at execution) is the mechanism that makes "there waiting" cheap — the surface pre-loads only L1 metadata, the model expands at runtime. The declaration contract (frontmatter schema + surface manifest) is harness-independent and PM-ownable; the pre-load is the harness's job. Source: MCP 2026 roadmap (modelcontextprotocol.io/development/roadmap; blog.modelcontextprotocol.io/posts/2026-mcp-roadmap), Anthropic Agent Skills spec, web-verified 2026-06-08.
- **Refinement — "the SDK solves skill selection" shrinks the problem, it does not remove the PM lane (2026-06-19, Ian Boston + Manas Garg)**: Ian named his greatest short-term concern as *"selecting which skill from a manifest… no different from AOv1… a solved problem for the Agent SDKs."* True, but only for **runtime selection** — the agent, at inference, picking which *already-loaded* skill to call (progressive disclosure: name+description loaded, model chooses). Skill selection actually has **four stacked layers**, and the SDK owns only the bottom one: (1) **runtime** (which loaded skill the agent calls — SDK-solved); (2) **surface/UI** (which skills a surface exposes, what the user sees and picks, per persona+context); (3) **governance** (which skills are authorized/available — admin/CoE, the [[Three-Layer AI Skill Governance Architecture]]); (4) **discovery/find at scale** (how the right skill is *found* among thousands to even be in the manifest — declaration standard + index + curation; Manas, same axis: *"nobody knows how to make this scale of skills available"* = open). The anti-pattern: hearing "the SDK solves selection" and concluding the PM work is gone. The correct read is the inverse — **the SDK taking the runtime pick is the hard plumbing done *for* you; what remains (surface + governance + discovery) is precisely the PM-ownable layer the SDK never touches.** "Solved by the SDKs" is a lane-clarifier, not a lane-eraser. Don't conflate the runtime pick with the find/govern/surface selection ([[feedback-dont-conflate-pattern-with-object]] in memory).
- **Where the layers live — the meta-harness taxonomy (2026-06-19, Felix Meschberger)**: a clean vocabulary that locates the split. A **harness** = the agentic loop itself (Claude Code, Codex — "what they call themselves"). A **meta-harness** = the infra that *runs* harnesses (Coworker, Anthropic Managed Agents), where a **manifest** (Coworker) or **agent** (AMA) *defines* the actual harness. So: the **runtime pick is the harness/SDK's job**, and the **non-runtime selection (surface + governance + discovery) lives at the manifest = the meta-harness layer** — which is the PM-ownable seat. The consensus path a peer articulated (*"teams build the skills, deploy them into Coworker, and define the manifest to implement the harness they need to execute the skills"*) is the decoupling thesis stated as architecture: skills are the durable layer teams own; the harness is manifest-defined and swappable; the meta-harness is plumbing. More swappable layers (swap the harness inside a meta-harness via the manifest; swap the meta-harness itself), so the portable skills + API substrate above them all is the durable hedge.
