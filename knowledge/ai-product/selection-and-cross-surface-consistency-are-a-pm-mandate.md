# Selection and Cross-Surface Consistency Are a PM Mandate

_Section: Distributed-Harness Architecture (AOv2 / Agentic NorthStar) — part of `ai-product/`; router = README.md._
- **Date identified**: 2026-05-22
- **Source**: Ian NorthStar thread. Verbatim: *"the UI deciding which harness to call"* (explicit or prompted selection, *not* automatic intent detection); *"UX, yes, absolutely, must be PM lead"*; *"Consistency will be vital so an Adobe user feels like it is the same surface regardless of the implementation details or UI engineering ownership."*
- **Insight**: In a distributed-harness model two things become **product (PM) problems, not architecture**: (1) **Selection** — which harness/agent a request routes to. The UI decides; *explicit or prompted* selection beats *auto intent-detection* (the seductive option that burned trust in AOv1, where the orchestrator inferred intent and routed wrong). (2) **Consistency** — making independently-owned, distributed surfaces feel like one coherent Adobe product. Consistency is in direct tension with distributed UI ownership; reconciling it is the PM mandate, and the architecture-backed answer to "too many surfaces / 4-chats" fragmentation.
- **Implication**: selection-as-UX and cross-surface consistency are the differentiator and the PM's lane (architect put it on record). For AEM this elevates the hero surface (Experience Hub) from a launchpad to the **selection + consistency layer** of the distributed agent architecture.
- **Refinement — the concrete mechanism of cross-surface *continuity* (2026-06-05, EH→EW handoff case)**: when two surfaces are two UIs on two separate harnesses (EH home + Experience Workspace), making one experience span them ("start in EH, deep authoring opens EW, conversation + context carry") does **NOT** require merging the harnesses or putting both on the same engine. It requires **three things shared *above* both harnesses**: (1) a **shared memory/session** keyed to IMS identity (one surface writes, the other reads), (2) a **shared skills/prompt inventory** (a skill invoked on one surface is the same one the other continues — declared once, reachable from both), and (3) a **handoff** (surface A deep-links into surface B passing the session reference + prompt). The harnesses stay separate; continuity lives in the substrate above them. **This is why "distributed engineering, unified experience" is mechanically possible, and why cross-surface continuity is engine-independent** (it does not depend on both surfaces running the same harness). Practical sequencing: the shared skills inventory is the nearer-term piece; the shared cross-surface memory/session is the harder, often-missing piece (a real platform dependency — e.g. Ian's memory service). The PM owns the **cross-surface experience requirement + the handoff contract** (what continuity must carry, grounded in a concrete user moment); the platform owns the **memory service** that fulfills it — own the requirement, not the implementation.
- **Refinement — heterogeneous build substrates force the check-path, they don't permit the components-path (2026-06-05, EH vs EW evidence)**: there are two ways to make distributed surfaces consistent — *build it the same* (shared design-owned components, identical by construction) or *check it's the same* (write the definition, let teams build freely, conform each surface to the definition + flag drift). Which is available is **not a free choice when surfaces already run different component systems.** Observed: Experience Hub uses a custom UI framework; Experience Workspace builds on the DA-NX component library. Because they share no component substrate, consistency between them **cannot** come from shared components — only from a definition + a check that spans both. So the more heterogeneous the surface estate (and a distributed-harness world trends that way), the more the check-path is the *only* one that scales across all of it; shared components remain valid **within** a substrate (a surface that already has them uses them), never **across** independently-built ones. Practical: the consistency definition must be **readable by an LLM** (markdown) precisely so the check works against any surface regardless of how it was built. Don't propose shared components as the cross-surface consistency mechanism; propose the definition + check, and let shared components be one surface's internal way of meeting it.
- **Refinement — selection is two-step, and the per-surface default is *curated*, not derived (2026-06-23, "Pre-load, Don't Limit" published, wiki 3941701071)**: the concrete mechanism that makes surface pre-load actually improve selection (the missing "how" under the mandate). (1) **Two-step beats one-step** — route to a *domain* first (a handful: Content / Governance / Assets / Developer, reliable), then pick the skill inside that domain's loaded set (small pool, reliable). AOv1's ~50% right-skill / ~5% happy came from one selection over everything at once; shrinking the *active* candidate pool is the lever (Ian: one-manifest-per-team would have selected far better). (2) **The cross-domain hole** — most real requests cross domains ("update this page and check it's on brand" = Content+Governance), so a rigid domain-only default misses the right skill and falls back to whole-library search (the 50% returns). **Fix = PM-curated defaults**: review what users actually do on a surface and curate the recurring cross-domain skills into its default → the default is shaped by the real workflow, not the org chart = the **measurement→curation loop** (selection feeds reporting, reporting feeds curation = the PM lane at both ends). (3) **Scope honesty** — pre-load/selection fixes the **50% (is the right skill chosen)**, NOT the **5% (skill quality / was the customer happy)**; the 5% is a separate problem, measured by acceptance rate, not by selection. (4) **Declaration consequence** — the skill's `domain` (home) field becomes load-bearing (drives step 1) alongside `when-to-use` (drives step 2); **one** home-domain per skill, and cross-domain *placement* lives in the surface manifest (PM-curated), not on the skill — keeps cross-domain curation in one place instead of scattered across every skill. The "pre-load, don't limit" framing: the surface auto-loads its default, the rest of the library stays reachable on demand (pull/discovery), never dumped into the same selector. Published as the 3rd in the series ([[Pre-load, Don't Limit]]), framed as the Bucharest proposals (there-waiting + surface map) applied to Coworker and the answer to Bertrand's EPA-in-Coworker question.
- **Sharpening — "small" is not the bar, "small AND non-overlapping" is (2026-06-23, Ian Boston reply, NOT a confirmation)**: Ian reserved judgment on the two-step framing (*"I don't know yet… currently researching with Claude"*) and flagged the real gap from his Codex analysis: *"don't reason over > 20 skills… it's the catalog size that matters and the distance between each skill. Overlaps will create problems and the same behaviour seen in AOv1… it only takes 2 skills to overlap for the wrong one to be chosen."* (Also: AgentSDKs don't solve what Coworker attempts — severity depends on what's in the manifest; Codex is more context-efficient than Claude, so the skill-count ceiling is *lower* on Claude.) → **Three corrections to the mechanism, honestly:** (1) shrinking the per-surface catalog *reduces where* overlap can happen but does **not** remove overlap *inside* the pool — so the curated default must be small **and** de-overlapped, not just small; (2) the per-skill **"when to use" is the lever that raises Ian's "distance between skills"** (separates near-duplicates so the selector can tell them apart); (3) overlap can be **audited** two ways — static (embed description + when-to-use → pairwise similarity → flag near-duplicate pairs) and empirical (run representative prompts, measure right-skill-rate, surface the *confusion pairs*) — but the audit **finds, it does not fix** (resolution = sharpen/merge/drop, and it is cross-team), must run **continuously** (every manifest change re-introduces overlap), and **reduces, not eliminates** wrong-pick probability. The overlap audit + right-skill-rate = the measurement→curation loop made concrete = the data answer to Ian's "the problem hasn't gone away" (you don't make it vanish, you detect + manage it per surface, with numbers, not hope). **Discipline check ([[feedback_dont_overread_vp_quotes]]):** Ian's Codex points are *consistent with* the small-catalog direction but he explicitly withheld endorsement and leaned skeptical — log as a sharpening + reserved judgment, NOT as validation.
- **Quantified — the benchmark behind "non-overlapping," and the three numbers to carry (2026-06-23, Ian's two Codex analysis docs: `skills-mcp-context-limits.md` + `ao-react-skill-selection.md`, git.corp.adobe.com/boston/experiments)**: Ian's own harness analysis put numbers on the lane. The `ao` ReAct service (= AOv2 / CoWorker lineage) ran a 661-case skill-selection benchmark (Opus 4.6, aep-aia manifest, **~13 skills directly visible**): **overall 0.763 strict / 0.827 lenient**; `operational-insights` dragged to **0.705** purely from **sibling confusion** (near-synonym skills `operational-insights` vs `operational-stats-causal-analysis` vs `cja` mis-picked). **Three load-bearing findings:** (1) **the binding limit is selection precision, not token budget** — at ~13 skills the budget is a non-issue; *description overlap* drives every miss, confirming "non-overlapping" is the real bar (the docs: "sibling confusion dominates the misses, not catalog size"). (2) **Progressive disclosure / deferral raises the *ceiling on how much you can carry*, it does NOT raise *accuracy of choosing within what's visible*** — the same ~76–83% ceiling holds across Codex, Claude Agent SDK, and ao; the *only* lever that moves quality is keeping the **directly-visible tier small AND lexically distinct.** → corrects any "pre-load the surface default and selection improves" optimism: pre-load helps *only if* that default tier is de-overlapped; two siblings in the same surface default crater accuracy regardless of size. (3) **The deferred/on-demand tier ("reachable, not locked out") carries a recall cost** — ao's search is **regex/keyword, not semantic, returns max 5**; a skill is missed if the query doesn't lexically match → "the rest stays reachable on demand" is **not free**, and the per-skill `when-to-use` doubles as the search-match text (embeddings would raise recall). **The >90% bar vs reality:** Ian wants manifests sized so accuracy is *guaranteed >90%*; measured today is **76–83%** → the gap is real, named (overlap among visible siblings), and closing it = cross-team description discipline = governance = the PM lane. **Cost-per-run reality (for exec framing):** a "modest" ~13-skill visible catalog already burns **~263k input tokens/run** (reminder + chosen-skill body + ~7-call ReAct loop) against a hard **400k context cap** (even 1M models capped) — so the catalog must stay lean to leave room for the actual work (diffs, file reads, tool outputs), which is what really fills the window. **Reconcile vs Ian's Slack paraphrase (don't quote his round numbers raw):** "400K tokens per iteration" = the *window cap*, not per-iteration; "Codex 100K for 20 skills" = *run content*, not catalog (Codex catalog cost ≈ 30–100 tok/skill frontmatter). Carry instead: *"~13 visible skills already ~80% accuracy and ~250k tokens/run; overlap, not count, is the wall; >90% needs de-overlapped, distinct descriptions per surface."* **Discipline ([[feedback_dont_overread_vp_quotes]]):** these are Ian's *commissioned* docs and he still reserved judgment — they supply the receipts + the >90% homework, NOT an endorsement of Pedro's model.
- **Measured — the static overlap audit, built and run (2026-06-24 POC, lexical TF-IDF on `description`, 128 real skills across 4 live AEM agent marketplaces: aem-aia 12 / excat 54 / EPA-experience-generation 15 / forms 47)**: the first numbers on the *static* half of the audit. **Two findings:** (1) **overlap tracks domain proximity, not team count** — cross-agent lexical overlap stays low even in a shared domain (EPA↔excat content-authoring max 0.10; Forms↔EPA max 0.10), while the measurable confusion is **within an agent** (siblings: forms-plan↔forms-plan-ntb 0.86; commerce-migration-pdp↔plp 0.86; quiet-hours↔update-free 0.41) → refines "more skills = worse" to **"more skills in the same *domain* = worse"**, which makes a home `domain` field the audit's clustering key (audit overlap *within* a domain, across teams). (2) **The format gap is real and large** — no `domain`/`when-to-use` fields exist; when-to-use is crammed into one free-text `description`; **108/128 (84%) of skills carry incomplete disambiguation** (54 none, 54 partial) = the hard number behind the structure ask. **Honest scope (1 lexical run):** semantic embeddings + the empirical confusion-pairs (right-skill-rate, likely in `Adobe-Experience-Platform/ao` `evals/`) are the next passes and the bar Ian set; do **not** pitch this as "huge cross-team overlap" — the lexical data shows the opposite (intra-agent dominates). The static audit + the proposed `domain` + `when-to-use` fields = the governance mechanism made concrete, with the agent-owner CTA published in the POC report. Still a refinement, not a new entry (1 POC obs).
- **Sharpening — "within an agent" ≠ "within one team" when the catalogue is SHARED (2026-06-25, Sergiu/EDA fact)**: the AI Assistant catalogue `aem-aia-extensions` is a *shared* marketplace — multiple agent teams contribute skills into it (Experience Development / Sergiu provides skills there; `quiet-hours`↔`update-free` 0.42 = his pair, not the AI-Assistant-PM's). So a confusion pair that reads as "intra-agent" in the audit can in fact be **cross-team** when it sits in a shared catalogue. Two consequences: (1) the audit must key on the *contributing team*, not the catalogue label; (2) route the report + the fix **per-skill to the contributing team**, not to one "catalogue owner." The intra-agent-dominates finding holds *per contributor*; the shared catalogue is where cross-team overlap can still hide. Distribution lesson (the convening lane): post the report to a shared migration channel (`#aem-agent-ex-modernization`, Mike Tilburg's pointer) + tag the skill owner rather than DM each team — info pulls from a durable surface.
- **First-party sourced — selection is manifest-scoped (not global), and the platform's OWN selection eval already exists (2026-06-26, read directly from `Adobe-Experience-Platform/ao`)**: two things confirmed first-hand from the AOv2 monorepo (not via Ian's paraphrase). **(1) Co-presence is manifest-scoped, settling "do all skills compete together?" — no.** The code separates a publish-time **catalogue** (`agent_platform/plugins/catalog/catalog.py`: `# Available (not scoped)` vs **installed** scoped) from a **manifest** that installs a per-customer/org/user subset (`.ao/manifests/aep-aia/` — `cx-coworker-*.yaml` per customer, `aem-*.yaml` per agent; `aem-aia.yaml` removes inherited AEP plugins via `disabled_plugins`); the LLM selects only over the manifest-resolved installed+visible set (`agent_platform/skills/reminder.py`; deferred skills narrower still via `skill_search`). 4-layer scope: platform → application → tenant(org) → owner(user). **Mental model:** catalogue = app store; manifest = what's installed on one customer's phone — the model picks from the installed subset, not the store. **Consequence for the lane:** overlap is bounded to whatever a manifest makes co-present (a cross-catalogue audit over-counts the theoretical surface), AND **selection is testable BEFORE Coworker GA** by building a manifest with a chosen visible set and running the eval — the third path between "ship untested" and "wait for GA," and the sourced answer to Bertrand's "you can only test a skill with all the others on Coworker." **(2) The empirical confusion-pairs Ian asked for already exist — point, don't generate.** The platform's own eval: `benchmarks/v1_skill_selection_baseline/` (PR #2400, merged 2026-05-19; design doc `…/skill-selection-eval.md`, author Zhengyuan Zhu / reviewers Yunyao Li, Guang-Jie Ren, Shalini Gupta, Michael Shavlovsky). Metrics: strict/lenient accuracy, per-skill recall, **`confusion_pairs_top_10`**, coverage, selection_consistency; **Phase 0 = 0.763 strict / 0.827 lenient on 661 cases** (`aep-aia` manifest); co-presence controlled by editing the manifest (Variant A "10 real masked, 31 stubs"; B "41 visible"). **Phase 0.9 paused 2026-05-28** for production traces (audience-creation 0/134, dx-api bypass 68, 46% empty). Overlap is a named prod failure: the **"April AEM Customer Service Outage" = cross-agent description collisions hit production** ("collisions detected; gating wasn't"). This is the platform's first-party eval (distinct from Ian's personal Codex docs above) = the data answer to "the problem hasn't gone away." **(3) The static audit reproduced** at 132 skills via a standalone harness (`/Users/pedrofer/GitHub/adbe-skill-audit`, local-only) — same shape: worst pair 0.894 (`commerce-migration-plp↔pdp`), 0.86 (`forms-plan↔ntb`), 18 pairs ALL intra-agent, zero cross ≥0.35 — reconfirming overlap = domain-proximity, not team-count. Still a refinement (sourced sharpening of the selection chain), not a new entry. Sources first-hand via `gh`/`pedrofer_adobe`; flagged inferences: segment→org binding + plugin-repo SKILL.md internals not traced end-to-end.
- **Sharpening — marketplace ≠ manifest; "unify the skills" means converge the MANIFEST, not the marketplace (2026-06-26, live-verified against `Adobe-Experience-Platform/ao` + the 4 AEM repos)**: the reflexive ask when leaders see scattered skills is "put them in the same marketplace." Wrong unit. **A marketplace is a *catalog source*** (a GitHub repo with `.claude-plugin/marketplace.json`, registered + shallow-cloned for browsing); AEP's plugin/marketplace design (`docs/reference/domains/plugins-and-skills/`, author ssree) **supports many marketplaces by design** — the architecture diagram lists "Marketplace Repos (GitHub)" plural. **The manifest is the convergence unit:** plugins/skills install into a manifest (scope application > tenant > user, most-specific-wins), the manifest is the runtime co-present set, and a `plugin_ref = plugin@marketplace` lets **one manifest bind plugins from N marketplaces**. So the de-overlap / selection work happens at the manifest, never by merging repos — teams keep their own marketplaces, you curate the manifest. **Two consequences:** (1) for the empirical eval owed to Ian, the move is *construct an AEM manifest that makes candidate skills co-present, run the eval over it* — the manifest IS the test-harness scope (no marketplace surgery). (2) **The "4 AEM marketplaces" framing is loose** — live check: only **2 of 4 repos are real marketplaces** (`aem-aia-extensions`, `epa-experience-generation-extensions` carry `marketplace.json`); `aem-experience-catalyst` is a full standalone app and `forms-skills` is custom-packaged (neither has `marketplace.json`), so Forms + excat must be repackaged to enter AOv2 at all. Banked → [[reference_aov2_marketplace_manifest]]. Refinement of the manifest-scoped selection entry above, not a new entry.
- **Sharpening — the migration bridge is a delivery-timing question, NOT a test-environment question; co-presence is set by the manifest, not the bridge (2026-06-26, Bertrand thread + Pedro correction)**: Bertrand's worry was the bridge "deports skills from where they'd be tested (Coworker, with all the others)." It does not. The bridge (Plan B) still **puts the migrated skills into an AOv2 manifest** (slide verbatim: *"integrate into an AOv2 manifest consumed by EPA as a technical agent through A2A"*) — so the skills are co-present with that manifest's siblings either way. **Nothing runs as a lone skill** ("isolated behind AIA" was a mis-framing Pedro corrected); on Coworker skills already run many-per-manifest today (`aem-aia` = 7 plugins + inherited AEP). The only variable is **which skills share a manifest** = a manifest-composition choice, identical whether reached via the bridge or native Coworker. **Selection is therefore testable now, on an existing Coworker manifest, independent of the bridge** — the platform eval already ran on `aep-aia` (661 cases). So: (1) bridge = deliver skills to AIA customers before Coworker GA (temporary A2A wiring = throwaway; the AOv2 skills themselves are durable); (2) selection validation = a Coworker manifest with the chosen skills co-present — already possible, the real GA gate, unrelated to the bridge. The only thing never co-present today = skills from **different agents** (each agent = own manifest), true with or without the bridge — cross-agent co-presence is a manifest-design choice, not a migration milestone. Don't conflate "skills delivered via the bridge" with "where selection is validated." - **Sharpening — "won't v2 reproduce the v1 routing failure?" — no, because the two layers fail differently, and only one is an LLM guess (2026-06-26, Bertrand thread + architecture verification)**: the natural exec objection ("manifest-scoped selection just moves the v1 routing problem up a level — now you route to the right *manifest*"). It does not hold, and answering it precisely requires getting the v1 mechanism right. **AOv1 had NO skills** — it was an orchestrator agent routing to *other agents*, guessing intent blindly; the v1 "50/50" was **blind agent-routing with nothing to distinguish** (not skill-overlap — skills didn't exist in v1). v2 splits that one blind guess into two layers that fail differently: (1) **which manifest** = resolved deterministically by scope/identity (org + surface + user), *in front of* the LLM — config, not a prompt-intent guess, so the v1 mis-route can't recur here (a manifest is a scoped *set of skills*, not a runtime routing target — a stakeholder asking "route to the right manifest" is often conflating the two); (2) **which skill within the manifest** = the only residual guess, and the one that *can* reproduce the v1 failure if skills look alike — which is exactly why the skill-**description** work (`domain` + `when-to-use`) + the overlap audit is the answer, not a side-project. So the crisp line: v2 removes the guess from the routing layer (deterministic manifest) and makes the remaining guess *measurable* at the skill layer (descriptions + audit), where v1 had a single blind guess with nothing to distinguish and no measurement. The skill-description work IS the answer to "won't we have the same problem." Refinement of the manifest-scoped selection entry, not a new entry.
