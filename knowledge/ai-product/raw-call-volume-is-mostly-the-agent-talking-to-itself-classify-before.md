# Raw Call Volume Is Mostly the Agent Talking to Itself — Classify Before You Headline

_Section: Measuring AI Features — part of `ai-product/`; router = README.md._
- **Date identified**: 2026-06-30
- **Source**: Pedro, AEM MCP usage analysis (Splunk `aem_mcp_usage`, Christian Meyer / Jabran / Tanju Erinmez), 2026-06-30. Convergent with Bertrand's 2026-04-02 ratio-vs-baseline framing and the locked "Tool Calls not requests/interactions" terminology.
- **Insight**: In MCP/agent traffic the headline count (requests, or even "tool calls") is a vanity number because **most of the volume is the agent operating the low-level API, not delivering a named outcome**. Measured on AEM's three MCP servers over 30 days: **~14.4M tool calls, but ~99.8% are the GENERIC API tools** of the One AEM MCP server — `lookup-api-spec` (the LLM pulling the API spec, Tanju's "whispering mechanism into the LLM's ear") = **51%**, `read-api` = 35%, `list-environments` = 7%, `write-api` = 6%. **The value/adoption signal is the SPECIFIC, intent-mapped operations** (`get-page`, `write-fragment`, `get-aem-fragment` …) = ~0.2% of calls. **Crucial correction (Christian Meyer, the dashboard owner, 2026-06-30): `write-api` is NOT the value cut — it is a generic building block to skip, same as read/lookup.** The agent composing raw REST writes is still plumbing; value = the named semantic tools. So "14 million calls" shown to a VP reads as massive adoption while the actual outcome layer is a sliver.
- **The method (requests → value)**:
  1. Stop leading with requests (the HTTP/edge layer — conflates session-setup chatter with action).
  2. Report at the **tool layer**, and split tools into **generic API plumbing** (lookup/read/write/list — skip, even though they dominate the count) vs **specific intent-mapped operations** (the named domain tools — get-page, write-fragment …).
  3. Headline the **specific-tool count** — that is the honest BVR capability-count, not the raw total and not the generic write count.
  4. Always **pair volume with retention** — reach ≠ retention (the same data: 497 orgs touched, only 33 "regular" ≈ 6.6% sticky). A big volume number can hide trial-heavy / daily-light usage.
- **Why it compounds (the trap)**: raw-volume metrics are self-flattering — they grow with the agent's own chattiness, so a dashboard can show "up and to the right" while value and stickiness are flat. The PM who strips the setup traffic and reports the value layer owns the **interpretation layer** over the raw counts — a cross-org positioning move, not just a cleaner chart.
- **Relationship to BVR**: BVR says *restore the volume signal with a capability-level monthly count*. This says *that count must be derived from value-bearing calls, not raw traffic* — the two are the same discipline from opposite ends (add the right volume back; strip the wrong volume out).
- **🔬 Extension added 2026-08-03 — classification is only one of three axes, and the other two bite just as hard.** On 2026-07-24 five separate headline numbers were produced in a single KR-update session and **every one was a measurement artifact until three properties were pinned**. Classification (this entry's original subject) was only the first:
  1. **Scope** — *what population is in the denominator?* The playground's *"External Orgs: 1"* reads as catastrophic failure and is correct by design: the aem.now playground runs on a single `aemsitestrial` tenant. Reported from the external-only cut it is a "failure"; reported from the full-playground view (Customers / Partners / Adobe / Personal) it is normal.
  2. **Window** — *what period, and is the instrument still on it?* The Modernization dashboard had silently stayed on Jun 15-21 while being read as current; caught before it was reported. A stale window produces a confidently wrong trend.
  3. **Basis** — *is this a calendar-to-date count or a rolling window?* The 847-vs-539 conflict was **not a data bug but a label collision**: 539 = distinct users, July calendar month-to-date; 847 = a rolling ~28-day active count, ~1.5× by construction and uniformly so across all five agents. **Diffing a number on one basis against a baseline on the other manufactured a "-19% MAU decline" that did not exist** — an error produced inside the analysis itself and corrected the same evening.
  **The rule this adds**: before any number is headlined, state its **scope, window and basis** out loud, and **never diff two numbers whose bases you have not confirmed match**. Classification tells you *which calls count*; scope/window/basis tell you *whether two counts are comparable at all*. Most cross-instrument "trends" are basis collisions.
  **The meta-finding worth keeping**: three reporting instruments in one day each produced a misleading headline until these were pinned. When a measurement layer produces artifacts at that rate, **harden the layer before headlining anything from it** — the credibility cost of one retracted exec number exceeds the value of several fast ones.
- **Application**: For any agent/MCP adoption report, decompose total calls into setup/read/value before quoting a number to leadership; lead with value calls + retention; and pin scope/window/basis before comparing anything to anything. The build gap to watch: per-tool data often isn't joined to the customer/external identity, so "value calls per customer" needs that join (the AEM CloudWatch open point).
